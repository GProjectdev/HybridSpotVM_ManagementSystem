위험률 변경에 따른 여러 Worker의 일괄 전환 — 2026-11-18

목적과 범위
현재 단일 교체는 source 1개/new 1개마다 full-world RestoreRequest를 만든다. 4-Rank의 1OD+3Spot→4OD에서는 전체 world를 세 번 복원할 수 있다. 새 경로는 기존 정책이 선택한 목표 market 구성을 바꾸지 않고, 동일 정책 결정에서 교체가 필요한 worker들을 한 번에 준비하고 기존 full-group RestoreRequest 하나로 전환한다. 역방향 4OD→1OD+3Spot도 동일하다. 위험률 알고리즘·CRD·Member restore/fencing 프로토콜은 변경하지 않는다.

설정
NodeRequest metadata.annotations:
  training.dcnlab.com/planned-partial: "disabled"
  training.dcnlab.com/group-replacement-batch-size: "3"
spec.replacement.enabled: true
batch-size는 1..min(worldSize,4). 미설정 또는 1이면 기존 단일 교체다. 3이면 3개 mismatch까지 하나의 operation에 포함한다. 이는 추가 VM 동시 점유를 명시적으로 제한하기 위한 opt-in 설정이다. 4-Rank에서 size3은 최대4+3=7VM, size2는 최대4+2=6VM을 동시에 보유할 수 있다. 직접 Spot 장애·FIS emergency는 기존 단일 victim 경로를 유지한다. 새 위험률·가격 모델을 만들거나 smoothing/trace-clock/학습 목표를 변경하지 않는다.

실행
1. 기존 정책의 ordinal별 market mismatch를 모은다. 과거 Verified source 종료 대기/고정 target/active SpotReplacement gate를 유지한다.
2. 전체 Rank의 durable checkpoint, 현재 world Pod UID, 공유 PVC 및 모든 source NodeProvision UID/Ready/market/node를 먼저 검증한다.
3. 기존 periodic checkpoint quiescence를 확인하고, 선택한 old UID/목적지 이름/market을 하나의 immutable operation annotation에 저장한다. controller 재시작은 이 intent에서 재개한다.
4. VM management의 GroupCapacityReconciler가 목적지 NodeProvision과 전파 정책을 모두 준비한다. 각 목적지는 고유 old UID와 공통 operation에 묶인다. 원본 SSH key/fence 설정은 상속하지 않는다.
5. Checkpoint/recovery의 GroupRequestReconciler는 모든 목적지가 서로 다른 새 Ready node일 때만 4-Rank target mapping을 포함한 RestoreRequest 하나를 생성한다. 일부 미준비/생성 실패면 원본을 유지하고 복원을 시작하지 않는다. 새로운 request마다 checkpoint를 혼합하지 않는다.
6. 기존 Member fencing/restore/release/Verified 경로가 네 Rank를 처리한다. 원본 current Pod UID와 checkpoint archive provenance를 구분한다.
7. Verified 뒤 모든 목적지의 실제 UID/Ready와 모든 잔존 source UID를 먼저 검증하고, 정확한 원본들을 UID precondition으로 정상 삭제한다. finalizer나 AWS 종료 확인은 우회하지 않는다. NodeProvision 종료가 남으면 다음 batch 할당을 막는다.
8. 모든 pair의 successor chain을 기록한다. 원본이 아직 남아 있어도 Verified successor가 inventory를 우선하며, 반대 방향 후속 전환도 해당 leaf의 UID에서 이어진다.

소유 관계와 계측
추가 CRD 없이 group-operation annotation의 Batch 배열에 준비 의도를 저장한다. RestoreRequest의 training.dcnlab.com/group-replacement-pairs에 old/new 이름·UID 전체 목록을 기록한다. 기존 primary pair annotation은 호환성을 위해 유지한다. 정책 UID/generation, 중복 이름/UID, source world, 목적지 market/operation, 새 node 중복을 검증한다.

실패 및 제한
목적지 일부가 실패하면 batch를 자동 분할하거나 원본을 선제 종료하지 않는다. 기존 provider의 정상 재시도 또는 실험 watchdog의 suspend/UID 기반 정상 정리가 필요하다. 이번 변경은 자동 timeout/cancel/위험 재변경에 따른 준비 VM 회수 기능을 새로 추가하지 않는다. 진행 중 operation은 고정되며 위험률 변경으로 목표를 덮어쓰지 않는다. 새 위험은 현재 operation과 원본 종료가 끝난 후 후속 정책에서 반영된다.
Checkpoint를 VM 부팅 전에 quiesce하는 기존 방식은 유지한다. 따라서 최신 학습 step보다 이전 durable round로 rollback될 수 있다. rollback 감소/새 cutover checkpoint는 별도의 검증 항목이다.
CPU controller tests는 양방향 3개 목적지/1개 full-world request, 미준비 차단, UID/정책/receipt 오류, 원본 유지, 모든 대상 검증 전 삭제 금지, successor inventory, restart 중복 방지, 진행 중 목표 고정, batch2 상한을 검사한다. CPU fake-client 결과는 실제 GPU DDP batch 복원 성공이나 시간 절감을 입증하지 않는다.

배포 및 평가
spot-vm-management-controller와 checkpoint-recovery-coordinator 두 프로세스에 모두 새 코드가 필요하다. 한 프로세스만 업그레이드한 상태에서 batch를 활성화하지 않는다. idle 확인 후 두 이미지로 배포한다. Member 이미지와 CRD는 그대로 사용한다.
현재 평가 NodeRequest는 모두 정리된 상태이므로 활성 batch 실행은 없다. 정식 B/C에는 같은 batch-size·이미지·하드웨어·가격·CP bounds·위험 clock을 동결해야 한다. 7VM 피크와 최종4OD32vCPU를 실제로 수용하는지는 미확인이다. 배치 전환의 GPU 검증 및 전환 지연·중단시간·rollback·추가 VM 비용 측정이 남아 있다. 세 번의 restore를 한 번으로 줄이는 코드 경로와 end-to-end 실제 속도 개선은 구분한다.
