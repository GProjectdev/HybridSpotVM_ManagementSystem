IEEE Access 정량 평가 최종 구현·방법론 검토
파일: IEEE_Access_Evaluation_Review_20261118.txt
기준일: 2026-11-18, 시간 표기는 UTC 또는 명시한 KST(UTC+9)
대상: Hybrid Cloud Spot DDP 관리 시스템 / 졸업논문·IEEE Access 평가
평가 완료 목표: 2026-11-27. 본 문서는 측정 결과 논문이 아니라 코드·기존 증거에 근거한 최종 준비 검토다.

0. 검토 범위와 핵심 판단

[확인] 첨부 추가 요구 전체와 최종 평가계획 MD/PDF, 발표 원본의 추출 텍스트, 제공 Desai 원문 Cost_effective.pdf, 아래 다섯 저장소의 실제 정책·Controller·CRD 및 기존 수용검사 증거를 대조했다. 발표 원본은 변경하지 않았다. 기존 발표 E1/E2는 구현 시연 I1/I2로 취급하고 기존 E3 수치를 새 정량 결과로 사용하지 않는다. 앞서 별도 작성한 발표 개정 사본은 본 검토 이후 더 수정하지 않았으며 승인된 최종 발표자료로 간주하지 않는다.

[판단] 최종 E1/E2의 연구 질문은 타당하다. E1은 할인된 단가만으로 알 수 없는 실제 운영 패키지의 비용–시간 교환관계, E2는 단일 Spot rank 상실이 전체 동기식 DDP 운영에 추가하는 손실을 측정한다. 그러나 현재의 fixedOnDemand+고정 위험률 조건만으로 R2 동적 구성의 이득, R3 위험률 적응의 우수성까지 입증하는 것은 부적합하다. 이 둘을 이미 입증했다는 문구를 사용하면 안 된다.

[최종 결정] 핵심 6 GPU Run(2모델×3조건)을 최우선으로 유지한다. E1-B를 엄격한 동일성 검토 후 E2-A로 공유한다. 18 Run은 반복 확장 목표이며 필수 완료 약속이 아니다. R2/R3는 모든 핵심 Run에서 추가 GPU 없이 계측·적용 경로·운영 오버헤드를 분석한다. 정책 자체의 인과적 우수성을 주장할 경우에는 3절의 최소 별도 비교가 필요하다. 이 비교는 일정·유효성 gate를 통과할 때만 채택하며, 수행하지 못하면 논문의 주장을 통합 실행 및 한계의 실측으로 제한한다. 11/26~27은 결과 검증·표·그림에 남겨둔다.

[현재 미완료] 두 모델의 정식 E1/E2 정량 결과는 아직 없다. ResNet-50의 새 VM/FIS full-group 복원은 미통과 상태다. 오늘 G6에서 실제 두 rank 학습·durable Checkpoint까지 확인했으나 FIS template 생성 단계에서 실패하여 장애·새 VM 복원은 실행되지 않았다. 이를 성공한 E2로 세지 않는다. 선택 GPU/모델별 목표 step의 최종 동결과 FIS 수정 후 실제 수용검사도 남아 있다.

증거 표기:
[코드 확인] 현재 체크아웃에서 함수·조건을 확인함. 이 사실만으로 배포된 바이너리가 최신 소스와 같거나 실환경 경로가 통과했다는 뜻은 아니다.
[실측] 명시한 원본 로그/receipt에 기록된 관측. 시연·수용검사와 정식 평가를 구분한다.
[권장/계획] 사전 설계 선택 및 예상 일정. 실제 결과가 아니다.
[미확인] 원시 근거가 부족하거나 아직 실행하지 않았음. 누락값을 0 또는 성공으로 대체하지 않는다.

1. 현재 시스템의 실제 구현과 R1~R5 검증 상태

1.1 실제 배치·관리 경계

소스 경로 접두사:
H=/home/ubuntu/HybridSpotVM_ManagementSystem
P=/home/ubuntu/PublicCloud-VM-Provisioner_test
F=/home/ubuntu/My_FluidCR
V=/home/ubuntu/Karmada_with_PVMigration
S=/home/ubuntu/Stateful-Migration-Operator-with-PV
이하 H/internal/... 표기는 위 절대 경로를 뜻한다.

MGMT 실행 클러스터의 Pod가 Karmada API를 client로 사용한다. Karmada API 자체와 MGMT Kubernetes API는 별개다. 관리 Controller가 실행되는 클러스터를 Karmada API로 오인하면 안 된다.
- MGMT kubeconfig /etc/kubernetes/admin.conf
- Karmada /etc/karmada/karmada-apiserver.config
- AWS Member aws1 /root/aws-cluster/aws1.kubeconfig
- On-Premise Member /root/on-premise/member/onpre1.kubeconfig
오늘 읽기 전용 검사에서 네 API 접근 가능. 이는 모든 미래 실험 시점의 가용성 보장이 아니다.

H/internal/management/setup.go:componentControllers, SetupVMManagement, SetupLifecycle, SetupCheckpointRecovery가 실제 프로세스 책임을 나눈다.
- public-cloud-vm-collector: SpotRiskProfile 갱신, H/internal/collector/collector.go:Reconcile/collect.
- spot-vm-management-controller: PolicyReconciler, ReplacementCapacityReconciler, RecoveryReconciler, GroupRecoveryReconciler, GroupCapacityReconciler. 정책→초기 용량·대체 용량·검증 후 반환 담당.
- training-lifecycle-controller: NodeRequestBindingReconciler, DiscoveryReconciler, GroupPlacementReconciler. 실제 workload UID, 배치, Runtime 전파와 그룹 이전 연계.
- checkpoint-recovery-coordinator: CheckpointReconciler, ReplacementReconciler, GroupRequestReconciler. 주기/긴급 CP 및 복원·정리 요청 생산.
- placement-webhook: 배치 계약을 admission에서 보강. webhook Pod 제거가 API 허용을 뜻하지 않으며, 실험 때 현재 admission 조건을 확인한다.
Member에는 training-runtime-controller, node-local spot-watcher, Provisioner 및 C/R/PV 관련 실행기가 있다. spot-watcher는 IMDSv2 통지를 읽고 NodeProvision 상태에 전달한다(H/internal/member/spot.go:MetadataClient.Poll, SpotWatcher.Observe). Runtime은 실제 Pod UID 및 학습 endpoint 관측을 수집한다(H/internal/member/runtime.go:RuntimeReconciler.collect; iteration.go:aggregateIterationTiming).
구형 policy-manager/checkpoint-coordinator/training-runtime-collector 등의 cmd 이름은 별도 새로운 기능이 아니라 canonical 프로세스의 호환 alias다. 동일 책임 프로세스를 중복 배포하지 않는다(H/internal/app/run.go:leaderElectionID).

1.2 CRD·외부 실행 계약

H/config/crd/:
- noderequests.yaml: NodeRequest, training.dcnlab.com/v1alpha1. 문서상 TrainingPolicy 역할의 실제 wire API. targetWorkers, workloadRef UID, policy, checkpoint, capacity, replacement 및 status.policy/checkpoint를 가진다. 구형 명칭이 보인다고 두 활성 정책이 있다고 가정하지 않는다.
- spotriskprofiles.yaml: SpotRiskProfile. static/HTTPS/trace/paperEstimator 중 하나의 입력과 freshness/provenance.
- trainingruntimes.yaml: TrainingRuntime. workload/member UID, rank별 Pod/step, iteration 및 phase.
- spotreplacements.yaml, spotrecoveries.yaml: UID에 묶인 교체·반환 상태.
P/api/ml/v1alpha1/nodeprovision_types.go 및 P/config/crd/bases/: NodeProvision, NodeProvisionNetConfig, ml.dcn.ssu.ac.kr/v1alpha1. 실제 EC2 생성·join·GPU 준비·종료는 P/internal/controller/ml/nodeprovision_controller.go에서 수행한다.
S/config/crd/{fluidcrmigrations,restorerequests,restoreplans}.yaml: FluidCRMigration, RestoreRequest, RestorePlan. FluidCRMigration은 fluidcr.dcnlab.com/v1alpha1, RestoreRequest/RestorePlan은 migration.dcnlab.com/v1alpha1이며 실제 API group은 각 YAML의 spec.group을 따른다. H에 이름만 같은 로컬 임의 CRD를 추가하지 않는다.
V/config/crd/bases/migration.dcnlab.com_{pvmetadata,pvmigrations}.yaml: PVMetadata/PVMigration. V/config/karmada/ric/의 PV/PVC/PVMetadata interpreter와 S/config/karmada/ric/의 FluidCRMigration/RestorePlan interpreter가 전파·상태 집계를 보조한다.
Karmada PropagationPolicy→ResourceBinding→Work→Member 객체와 상태 반영은 기존 upstream 기능을 사용한다. V/internal/management/migration.go:BuildWorks, validateBinding, workApplied는 본 PV 연계층이다. 독립 PVC는 별도 PV/PVC Work 및 reciprocal binding receipt가 필요하다. NFS 공유 파일의 존재만으로 새 Member의 PVC binding/restore 준비를 대신하지 않는다.

1.3 R1: 요청 기반 GPU VM 생성·배포·종료

구현: 요청 생성·정상 삭제에 따른 공급/반환 경로는 구현되어 있으나 학습 완료 감지에 따른 무인 자동 반환까지 완료로 볼 수 없다. H/internal/management/policy_controller.go:PolicyReconciler.Reconcile, provisionBeforeWorkload; H/internal/policy/objects.go:NewNodeProvision; capacity.go:checkCapacityLifecycle 및 P NodeProvisionReconciler.Reconcile/reconcileAWSProvisioning/reconcileJoining/markNodeProvisionReady/handleDelete.
연계: 요청 UID→NodeProvision→EC2 provider ID/UID tag→Kubernetes Node→할당 가능한 GPU→실제 rank Pod. CR 삭제만으로 종료를 추정하지 않고 Provisioner 종료 처리 및 실제 EC2 state를 확인한다. 기존 net config/VPN/AMI 기반 bootstrap을 재사용한다.
기능 검증: 기존 G5 및 오늘 G6 생성·학습·정상 반환 관측 있음. 오늘 G6 EC2 i-02d8d85f94c087d24(Spot), i-0f97eb7294733df6c(OD)의 terminated와 두 임시 루트 EBS 부재 확인.
중요 구분: H/internal/management/setup.go에 등록된 lifecycle은 binding/discovery/group placement다. H/internal/member/runtime.go:collect는 Running 상태를 수집하며 학습 완료→Completed를 소비해 baseline NP를 자동 반환하는 별도 lifecycle 경로를 조사한 코드에서 확인하지 못했다. 평가 trainer는 hold_completed에서 completed event를 내고 관측을 위해 머물며, 종료·정리는 evaluation runner/운영 절차가 요청한다(H/evaluation/run.py:start/stop/cleanup; legacy runner이며 final namespace에 그대로 실행하지 않음). 따라서 현재 증거는 요청된 정리의 정상 실행이지 Controller 단독의 학습 완료 자동 감지·반환 성공이 아니다. 해당 end-to-end 자동 반환 기능은 미구현으로 판단되는 범위이며 별도 외부 구성의 존재는 미확인이다. 이번 허용 범위에서 core lifecycle을 새로 설계해 추가하지 않는다. 논문 R1 문구는 요청 기반 공급·정상 반환으로 제한하거나 이 공백을 명시해야 한다.
정량 평가: 정식 완료 전. E1/E2에서 초기 생성/Ready/startup/유휴/반환 지연과 전체 compute cost를 측정할 예정.
검증 부족: 임의 VM종류/AZ/실제 quota 전반, 실패조건 전체, 대규모 자동 확장. fixed targetWorkers 변경은 코드가 막으며 범용 elastic world-size 관리로 주장하면 안 된다.

1.4 R2: Spot 위험률 기반 VM 구성·실행 중 교체

구현: 초기 구성뿐 아니라 실행 중 market mismatch 교체 경로도 존재한다.
- H/internal/policy/contract.go:DecideAt(약361행) → 위험률·alpha·horizon·가격·fresh recovery economics로 목표 OD/Spot 수 산출.
- policy_controller.go:Reconcile → freshness/하드웨어·region 일치/workload UID/discovery·placement 확인 → capacity.go:checkCapacityLifecycle → ensureAutomaticSpotReplacement.
- 기존 NodeProvision marketType을 patch하는 방식이 아니다. 교체할 source NP UID와 operation을 고정하고 새 NP를 준비한다. replacement.enabled가 false면 replacement_required로 차단한다.
- planned-partial이 disabled가 아닐 때는 ensurePlannedPartialReplacement의 선행 조건이 필요하다. 증거가 부족할 때 전체 그룹 삭제로 자동 확대하지 않는다.
- planned-partial=disabled를 명시하면 H/internal/management/group_producer.go:ensureGroupReplacement가 완전한 recoverable checkpoint, source Pod 집합, NFS/PVC, schedule quiesce를 확인한 뒤 intent/capacity/request 단계를 거친다(group_operation_controller.go:reconcileGroupOperation).
- group recovery/cleanup 및 RecoveryReconciler는 Verify·fencing·소유 증거를 검토한 후 원본 NP 반환을 연계한다. Karmada 원본과 Member NP/provider를 모두 연결해야 한다.
- paper_residency.go:applyPaperResidency는 UID-bound Verified OD 복원부터 최소 OD 체류 시간을 적용한다. 기본 3600초. 위험 감소 즉시 무조건 Spot 복귀하는 설계가 아니다.

기능 검증: 과거 receipt-diagnostic-objects.json에서 SpotReplacement UID 0f93d9c8-cf79-469b-8b03-0a9b2a2dac06 Completed, RestoreRequest UID 032f4844-d48d-49c5-afa3-947dd7bee7db Verified를 확인했다. 같은 진단 집합에 cleanup SpotRecovery UID 47bd31e5-3af8-4f57-94fd-ddfd865d623b Rejected도 있다. reverse-policy-progress.json에는 partial 교체 선행 조건 미충족도 기록되어 있다. 과거 한 경로의 성공을 최신 generation·양방향 전체·모든 cleanup 완료로 확대하지 않는다. 이후 모든 최종 receipt가 있는지는 미확인이다.

정량 평가: 미완료. E1/E2의 fixedOnDemand 때문에 동적 정책 효과를 분리할 수 없다. 다만 actual VM state/NP UID/Pod progress를 통해 결정→VM Ready→restore→반환 latency 및 교체 구간 비용을 연결할 수 있는 코드/계측은 있다. 단순 정책 결정 로그를 실제 교체 성공이나 비용 이득으로 바꾸어 쓰면 안 된다.

1.5 R3: 위험·Runtime 기반 Checkpoint 조율

구현: H/internal/management/checkpoint_controller.go:CheckpointReconciler.Reconcile, checkpointState, applyPaperIntervalStatus; checkpoint_schedule.go:ensureCheckpointSchedule, scheduleMustPause, pauseCheckpointSchedules, syncScheduledEvidence.
입력·실행 계약: 현재 workload UID, fresh SpotRiskProfile, Runtime Running/모든 rank 준비/동일 checkpoint identity를 확인하고 source FluidCRMigration schedule 및 PropagationPolicy를 생성·갱신한다. Member 실제 scheduler/child round 실행 및 reflected evidence를 통해 측정 비용을 회수한다. 실제 scheduler는 S/internal/checkpoint/fluidcrmigration_controller.go:reconcileSchedule(약169행), updateScheduleFromCurrentChild, materializeReservedScheduledChild, scheduledRunReservation에 있다. full-rank/resume를 요구하고 pinned child UID 및 durable success를 확인하며 active round와 겹치는 새 round 생성을 막는다. 중복·inflight·복원 중 competing checkpoint 방지 및 no-catchup을 보장하려는 구현이다. 설정 주기와 실제 pause-start 간격은 같지 않을 수 있다.

실제 분기(핵심): H/internal/policy/contract.go:AdaptiveCheckpointInterval(약453행).
(a) risk-band-bootstrap:
  측정 비용이 없거나 stale/비정상인 기본 경로. ready rank 부족 시 60초를 bounds로 제한. 기본 밴드 lambda<=.02:600초, <=.05:300초, <=.10:120초, <=.20:60초, 초과:30초를 min/max로 제한한다. 이 밴드는 코드 fallback 정책이며 Desai가 이 네 경계를 검증했다는 근거는 없다. 사용자가 spec.riskBands를 주면 그 값을 우선한다. Runtime은 실행 준비 gate로 사용되지만 이 분기에서 Iteration Time 수치가 최적화식에 직접 들어가지는 않는다.
(b) checkpoint-cost-analytic:
  Paper가 비활성이고 checkpointSeconds>0, copySeconds>=0의 finite 실측 비용, 유효 observedAt, ready/nonnegative risk가 있을 때. 최대 나이는 maxInterval+600초. lambda_job/sec=lambda_per_hour*SpotWorkers/3600. 기존 optimalIntegerInterval에 C_checkpoint, C_copy, 시간 기준 1, lambda_job/2, bounds를 넣어 정수 주기를 계산한다. CRIU 실행 및 archive-export 비용에 대한 seconds-domain 적응이며 iteration을 직접 사용하는 비동기 DRAM 식이라고 주장하지 않는다.
(c) paper-equations-1-5-analytic:
  H/internal/policy/paper.go:SelectPaperInterval, PaperCheckpointCost. Paper.Enabled와 10분 이내의 실제 asynchronous GPU→DRAM/storage/buffer profile, 1분 이내 aligned optimizer-update-window-v1/max-rank-mean iteration, 전체 rank count/step/sample 일치가 필요하다. Eq3 목적함수와 Eq4 memory 제약을 만족하는 정수 argmin을 해석적 후보로 구한다. 원문은 sweep을 기술한다. 조건 미충족 시 bootstrap으로 fallback하며 CRIU 시간으로 async profile을 가짜 충족시키지 않는다.

[실측] 기본·비용 기반 분기는 실제 수용검사 snapshot에서 관측됐다. 오늘 G6 run의 15개 UID-bound snapshot에서 policy와 coordinator의 경로를 별도 회수했다. 초기에 runtime_not_ready/intervalSource 누락이 있었고, schedule_updated 뒤 bootstrap→checkpoint-cost-analytic으로 바뀌었다. acceptance의 bounds는 120/120초이므로 경로가 바뀌어도 간격은 120초로 고정됐다. controller cost 관측 20/10초, 이후 16/9초는 FluidCR 상태의 checkpoint/copy wall time이며 GPU→DRAM 측정값이 아니다.
[미확인] paper-equations-1-5-analytic이 현재 CRIU+학습 이미지에서 실제 async profile로 활성화되어 GPU 실험을 통과한 증거는 없다. 이를 최종 E1/E2의 기본 경로로 쓰지 않는다.
정량 평가: 동작/주기·stall 증거는 있으나 적응이 고정 주기보다 유리하다는 공정한 정량 비교는 아직 없다.

1.6 R4: Spot 통지·대체 VM·DDP 복원

구현: spot-watcher IMDSv2→NP status.spot→emergency_replacement.go:ensureEmergencyReplacement 및 emergency checkpoint, group/partial producer→S RestoreRequest/RestorePlan→Member restore 작업→TrainingRuntime 실제 진전→Verified→원본 반환.
H/internal/management/group_checkpoint.go:selectGroupCheckpoint/readGroupCheckpoint는 policy/workload UID, source cluster, 완료 generation, 전체 rank, 동일 round, SHA-256 및 file-store:namespace/sha256 durableRef/export 증거를 요구한다. 부분 snapshot들을 합쳐 완전한 checkpoint처럼 쓰지 않는다.
S/internal/management/restore.go:RestoreReconciler.Reconcile와 S/internal/member/{reconciler,group,group_job,staged,prepared_workload}.go가 대상 준비·fencing·복원 및 검증을 맡는다. F/operator/internal/controller/fluidcrmigration_controller.go:appCheckpoint/containerCheckpoint/resume는 기존 C/R 실행층이다. S/internal/checkpoint/fluidcrmigration_controller.go는 관리된 CP 연계층이다.
기능 검증: GPT-2 과거 FIS/Verified 증거가 존재하나 현재 모든 새 설정과 같은 정량 Run은 아니다. ResNet-50은 11/17 2OD 같은 Pod에서 5회 process C/R 및 10개 rank별 audit(model/optimizer/RNG/step) 통과, 최종 5000 step 및 두 rank parameter/optimizer digest 일치. 이것을 새 VM 복원으로 부르면 안 된다.
오늘 G6 ResNet 실제 새 VM/FIS 수용검사는 template 생성 실패로 장애 미실행. 미완료다.
정량 평가: E2에서 다룰 예정. 장애 하나의 성공으로 자연 선점 빈도, 예측 정확도 또는 모든 복원 방식의 우수성을 입증하지 않는다.

1.7 R5: On-Premise→Public Cloud 상태 이전

구현: V의 PVMetadata/PVMigration 및 PV/PVC Works/RIC, S의 RestoreRequest/RestorePlan/source fencing과 대상 검증, H lifecycle/group placement를 연결한다. 기존 Karmada 멀티클러스터 배포와 공유 NFS를 재사용한다.
기능 검증: 기존 발표 I1(원본19쪽)의 checkpoint/restore 및 후속 update는 과거 구현 증거. 이번 검토는 발표와 코드 및 기존 receipt를 대조했으며 같은 통과 경로를 재실행하지 않았다. 모든 당시 raw receipt와 현재 버전 동일성은 미확인으로 남긴다.
정량 평가: 새 E1/E2는 두 AWS Worker의 DDP이므로 WAN을 가로지르는 DDP나 R5 이전 비용의 정량 평가가 아니다. R5 비용·지연 개선을 논문 주요 결론으로 내세우려면 별도 통제 이전 비교가 필요하다. 현재 일정에서는 필수에서 제외하고 구현·적용 범위로 구분한다.

1.8 기존 기술과 본 연구 기여의 경계

채택 기술: upstream Kubernetes/Karmada 전파·스케줄링, NFS 및 동적 PVC, AWS EC2/FIS, PyTorch DDP 동기화, CRI-O/CRIU 및 기존 DDP C/R 내부 알고리즘, Desai의 availability/SARIMA·checkpoint/resource policy 아이디어.
본 시스템 추가 구현 범위: 요청→공급→workload UID 연계; risk freshness/provenance와 정책 상태 관리; source/member 상태 조율; CP 일정·긴급 이벤트·복원의 충돌 제어; UID-bound full/partial 경로의 안전 계약; durable archive/PVC/fence/restore verification 후 VM 반환; 운영·평가 계측.
다섯 repository의 모든 과거 코드가 본 연구자의 신규 발명인지, 기존 연구 코드의 정확한 줄 단위 원저작 관계까지는 미확인이다. 논문에서는 채택 C/R 기술과 본 관리 계층의 확장 파일/계약을 구분해 기술해야 한다. 새 위험 예측 알고리즘이나 더 빠른 C/R 엔진 개발을 기여로 쓰지 않는다. 단순 통합만으로 IEEE 기여가 자동 성립하지 않으므로 운영 실패 조건·조율 비용·재현 가능한 실측을 보여야 한다.

2. E1/E2 타당성 및 비교의 범위

2.1 E1: 정상 실행의 GPU VM 비용–성능
연구 질문: 동일한 DDP 유효 학습 목표를 수행할 때 2OD 대비 1OD+1Spot+실제 checkpoint 관리가 startup·stall·유휴·반환까지 포함하고도 비용 이점을 남기는가? 그 대신 완료시간/유효 처리율은 얼마나 변하는가?
필요성: Spot 할인율로 정상 학습 중 checkpoint 정체, 이미지 준비, VM Ready/종료 지연을 계산할 수 없다. 실제 시스템 효과는 전체 실행 경로의 합과 경쟁으로 결정된다.
비교군 A=2OD/주기 CP 비활성, B=1OD1Spot/현재 coordinator 활성. 이 비교는 자원 시장과 CP 운영이 함께 달라지는 '운영 패키지' 비교다. 비용 차이를 CP 적응 알고리즘만의 효과로 해석하면 안 된다. A에도 snapshot/audit/data contract는 유지하고 주기 CP만 비활성한다.
R1·R3의 운영 비용과 R2의 고정 구성 실행은 측정하지만 R2 동적 교체의 이득은 분리하지 못한다.
예상 불리한 결과: 짧은 학습에서는 부팅/종료 비용이 Spot 절감보다 클 수 있음; CP/공유 NFS/network가 완료시간을 늘릴 수 있음; OD도 비정상 지연을 겪을 수 있음. 이 경우 그대로 한계로 보고한다.

2.2 E2: 단일 Spot 상실의 DDP 전체 운영 손실
연구 질문: 동일 Hybrid 정상 실행에 비해 실제 Spot rank 한 개를 FIS로 중단할 때 목표 완료시간·총 GPU compute cost·rollback·학습 정체가 얼마나 증가하며 어느 단계가 지배하는가?
필요성: DDP rank는 all-reduce로 결합된다. 손실 VM 1대만의 정지 시간으로 전체 학습·남은 OD 유휴·대체 VM 중첩 비용을 예측할 수 없다.
비교군 B=Hybrid/no fault(E1-B 재사용 가능), C=완전히 같은 Hybrid/단일 Spot FIS. 정책/CP/데이터/하드웨어/image/goal/최소 OD/복원 route 동일. 실제 natural interruption이 있으면 '단일 FIS만' valid arm에서 분리하고 모든 시도 기록은 남긴다.
R4와 R1·R3의 통합 복구 경로·운영 penalty를 평가한다. 타 C/R 시스템보다 빠르다는 비교가 아니며 recovery on/off로 고의 실패하는 baseline을 만들지 않는다.
예상 불리한 결과: 새 Spot 확보 실패, 긴급 CP timeout, 전체 그룹 restore 실패, 복원했지만 high-water mark 회복 지연, 반환 지연. 실패·censoring을 평균 성공 시간에서 숨기지 않는다.

2.3 공통 통제와 편향

두 rank=GPU 1개인 VM 2대, 각 rank는 서로 다른 VM에 배치. required hostname anti-affinity 및 trainer requests/limits GPU=1 확인. 일시 교체 중 최대3대는 비용에 포함하고 world_size=3으로 부르지 않는다. 정상 Hybrid는 rank0=OD/rank1=Spot으로 고정하고 실제 provider market을 확인한다.
동일 비교 블록은 instance type/AZ/AMI/driver/runtime/image digest, NFS server/export 및 PVC recipe, 모델/데이터 manifest, 초기 가중치/optimizer/seed/global batch/전처리/목표 유효 step, CPU/memory requests, 통신 설정, checkpoint mode, emergency/restore route를 고정한다. G5와 G6를 같은 평균이나 하나의 pair에 섞지 않는다.
정상 baseline은 동일 operational comparison hash 및 최종 상태 감사·interruption=0·목표 완료·완전한 가격/VM 장부를 모두 통과해야 재사용한다(H/evaluation/final_protocol.py:compatible_baseline_config/reusable_baseline/compare_e2). 다른 모델, 버전, policy activation이나 CP가 다른 Run은 재사용하지 않는다.
순서는 사전 seed 20261118의 블록 순서를 사용한다. 반복을 못했으면 n=1을 그대로 표시한다. 동일 baseline 1개를 여러 fault Run과 비교해 독립 n이 늘었다고 주장하지 않는다.
모든 실행 시도에 supply fail, timeout, 사용자 취소, restore 실패, 코드 변경을 기록한다. 결과 확인 후 유리한 위험률·목표·장애위치를 바꾸지 않는다. 오류 수정 후 재실행은 새 Run과 deviation으로 남긴다.
2-rank·짧은 고정 목표·두 소형 모델은 대규모 LLM/elastic DP/수렴 정확도/WAN DDP를 대표하지 않는다. CIFAR-10 ResNet 결과를 ImageNet ResNet 벤치마크로 부르지 않는다.

2.4 정량 지표와 계산 정의(모든 실험 공통)

시간:
t_request=source NodeRequest 실제 생성 시각. t_first=양 rank의 첫 공통 optimizer step 완료 중 늦은 시각. t_goal=양 rank의 목표 step update 완료 중 늦은 시각. t_audit=최종 audit 종료. t_release=마지막 실험 VM의 실제 종료 경계(정확한 경계를 못 얻으면 관측 bound).
T_startup=t_first-t_request; T_E2E=t_goal-t_request; T_training=t_goal-t_first. t_audit-t_goal 및 t_release-t_goal은 별도 보고하며 비용에는 포함한다. E2E를 VM 종료까지의 service lifetime으로 바꿀 때는 별도 이름·정의로 둔다.
유효 학습량 U: GPT-2=goal_steps×2×batch_per_rank×512 tokens; ResNet=goal_steps×2×batch_per_rank sample presentations. rollback 재실행을 분자에 더하지 않는다. CIFAR 같은 이미지를 다른 epoch에 반복한 것은 새 고유 이미지가 아니라 presentation이다.
주요 운영 처리율 Q_E2E=U/T_E2E. 기존 metrics가 반환하는 U/T_training은 first-commit 이후 경과로 정규화한 warm-start 지표이며 첫 update 시간은 분모에서 빠진다는 한계를 표시한다. 순수 steady window 처리율은 (window 끝 step-시작 step)×global_batch(×seq_len)/window 경과로 별도 산출한다. 두 정의를 혼합하지 않는다.
CP stall: checkpoint_id와 현재 rank/Pod UID를 대조한 각 rank의 [checkpoint_pause, training_resumed] 구간 합집합 길이. 양 rank 시간을 단순 합산하지 않는다. complete interval만 계산하고 일부 resume가 없으면 '미확인/부분 관측' 및 coverage를 명시한다. cadence helper의 min pause→max resume는 group pause span으로 합집합과 이름을 구분한다. CR start→completion/export는 저장·전파·archive latency이며 application stall과 다르다.
Rollback steps=max(0, 장애 직전 마지막 공통 committed high-water step - 실제 restored checkpoint step). request step이 아니라 실제 saved/restored step 사용. 완전한 긴급 CP로 0이 나와도 조작하지 않는다. rollback tokens/samples=rollback steps×단위 학습량.
학습 재개 gap: 실제 진행이 멈추기 직전 마지막 공통 step→복원 후 첫 공통 유효 update. FIS notice 뒤 학습이 계속된 2분 전체를 중단으로 세지 않는다. 기존 high-water mark를 처음 초과한 시각까지의 loss-recovery gap도 별도 기록한다. notice/action/EC2 종료/fence/restore/Verified는 각각 다른 시각이다.
비생산 GPU VM-seconds=sum_i length(reviewed group no-progress intervals ∩ VM_i billed-running intervals). GPU utilization이 아니라 진전 없는 실행 VM 노출이다. 동시 2VM이 1초 정지하면 2VM-seconds이며 makespan 2초라는 뜻이 아니다.
비용 C_GPU=sum_i integral_running P_i(t)/3600 dt. 최초·대체·중첩·유휴·audit·종료 대기 실험 VM 전체 포함. 실제 Linux/shared/Used/RunInstances OD 상품, 정확한 AZ/type의 Spot 유효 가격 구간과 timestamped receipt를 연결한다. AWS 최소 과금/중단 특수 규칙은 해당 상품 규칙을 확인해 반영한다. LaunchTime→terminated polling × ODprice는 보수적 상한 추정이며 invoice가 아니다. pending/shutting-down을 확정 billed running으로 둔갑시키지 않는다.
OD/H cost 절감률=(C_OD-C_H)/C_OD×100%; 시간증가율=(T_H-T_OD)/T_OD×100%; cost per useful unit=C_GPU/U. 음수 이득도 그대로 보고.
E2 추가 완료시간= T_fault-T_nofault; 추가 비용=C_fault-C_nofault; paired ratio/delta와 개별 원시점을 함께 보고. 복구 단계가 겹치므로 단계를 단순 합쳐 E2E를 만들지 않는다. GPU compute에서 제외한 EBS/NFS/network/VPN/관리 노드/FIS 비용은 별도 명시한다. 전체 cloud cost라고 부르지 않는다.

3. R2/R3 보완 평가의 최종 결정(11/18 결정)

3.1 기존 로그로 반드시 할 분석: 추가 GPU 0 Run

R2: risk UID/generation/source/validUntil→policy decision time/desired OD·Spot→실제 NP UID/provider market/state→VM GPU Ready→현재 Pod/Runtime step→복원/반환을 연결한다. 각각 decision latency, desired/actual composition 일치 시간, provision/return latency, 중첩 및 no-progress 비용을 산출한다. E1/E2에 실제 market 교체가 없으면 교체 지연은 N/A이고 초기 구성과 장애 대체만 보고한다. 결정 로그만 있는 행을 실행 성공으로 세지 않는다.
R3: lambda/runtime readiness/iteration availability→실제 coordinator intervalSource→선택 interval→source schedule generation→Member child CP UID/start/completion/export→rank pause/resume→E2 rollback/resume를 연결한다. policy.status와 checkpoint.status가 다른 시점/경로일 수 있어 둘 다 남긴다. stale/inflight/runtime_not_ready 구간과 경로별 체류·coverage를 보고한다. controller 관측 CP cost와 실제 application stall의 차이 및 interval setting과 actual cadence의 차이는 본 통합 구현을 실제로 측정해야 알 수 있는 특성이다.
이 분석은 관리 시스템의 적용 비용·지연·안전 제약을 평가한다. 그러나 '정책을 끄거나 고정한 경우보다 개선'이라는 인과 효과를 제공하지는 않는다. 특히 fixed composition/constant lambda에서는 동적 R2 성능을 주장할 수 없다.
최소 계측 보완: 오늘 H/evaluation/management_evidence.py를 추가해 기존 snapshot에서 위 policy/coordinator 상태를 UID-bound으로 추출하고 누락값을 유지한다. 실제시각을 polling시각으로 대체하지 않는다. 현재 policy log producer에 없는 intervalSource를 추측해 채우지 않고 CR 상태를 우선한다. observer는 향후 존재할 stage 필드도 allowlist로 보존한다. core Controller 배포 변경은 하지 않았다.

3.2 R2 별도 비교: 동적 적응의 효과를 주요 주장으로 유지할 때만 필요, 최소 2 Run

제목/RQ: 위험 입력으로 요구되는 구성에 도달하는 지연과 그 과정의 DDP 운영 비용은 얼마인가?

판정: 조건부 적합. 실제 정책 차이가 없거나 시간 부족이면 생략. 보조 결과 없이 'adaptive가 더 효율적'이라는 결론은 부적합.

4.3 0.05/h의 근거와 실제 효과

선정 근거: 기존 준비 설정의 낮은 통제 위험률이다. Desai 원문·서울 실측·SkyPilot에서 .05를 이 실험의 최적 대표값으로 선택했다는 통계적 근거는 없다. 이 한계를 명확히 밝힌다.
코드상 위치: final config existing_risk_spec.staticLambdaPerHour=.05, poll30초. resource method=paper-eq6-7, alpha=.8, horizon3600초, minOD1, target2, fixedOnDemand1(Hybrid) 또는2(OD).
수학적 상태: 1시간 per-shard survival exp(-.05)=.9512294245, P=1-exp(-.05)=.0487705755. 이 확률은 가정한 지수 hazard 모델의 계산값이며 서울 실제 선점 확률 측정이 아니다. throughput threshold는 -ln(.8)/1h≈.2231435513/h. double 경계의 동등성은 부동소수점 오차가 있으므로 테스트/비교에 threshold 바로 그 값을 사용하는 것을 피한다.
VM 결정: fixedOnDemand가 최종 override다. .05를 .8로 바꿔도 fixed arm의 목표1OD1Spot은 바뀌지 않는다. 가격 fallback/economics 평가가 있더라도 fixed composition control이 최종 구성을 정한다. dynamic(no override)는 다른 조건이 없을 때 .05→1OD1Spot, .37026→2OD. 아직 recovery loss/price가 없으면 ThroughputOnlyBootstrap이며 Eq7의 두 조건 모두 실측으로 평가한 단계라고 쓰면 안 된다.
Checkpoint: 기본 final bounds60~600, custom bands/실측 비용/async profile 없는 ready2rank 조건에서 .05는 bootstrap300초다. .050001은120초, .01은600초, .20은60초. 이는 오늘 기존 Go DecideAt를 직접 호출한 OFFLINE_COUNTERFACTUAL report로 재현했다. GPU 성능 측정이 아니다. stale 비용/Runtime 부족/custom band에 따라 다르다.
첫 CP 뒤 checkpoint-cost-analytic이 활성화되면 C_checkpoint/C_copy와 Spot수에 따라 다시 계산한다. .05에서 '항상300' 또는 '항상600'이라고 쓰지 않는다. 현재 bounds 및 실제 C값에 따라600에 clamp될 수 있으므로 interval timeline을 남긴다. 오늘 별도 G6 acceptance는 min=max120이어서 모든 경로120이고, 과거 bootstrap1200 snapshot에는 별도 custom 설정이 있었다. 이를 현재 기본 final 설정과 혼동하지 않는다.
적절성: E1/E2의 낮은 위험·고정 VM 상태를 통제하고 운영 비용/장애 penalty만 분리하는 용도로는 사용 가능. 실제 위험 대표값·예측 품질·동적 자원 우수성 검증용으로는 부적절하다. .05 경계 근처의 밴드 민감성도 외적 타당성 한계로 공개한다.

4.4 최종 권장 입력(실행 전 고정)

핵심 E1/E2는 B: static .05/h 유지. 이유는 AWS 자연 hazard를 추정한다는 주장을 없애고 같은 risk/CP 조건에서 fault 유무와 운영 package 비교를 분리하기 위함이다. 위험률을 실측처럼 포장하지 않는다. E1-A의 위험/decision 로그도 저장하되 주기 CP 비활성 상태를 명시한다.
조건부 R2 dynamic 비교는 A: 이미 잠근 first-held-out public SARIMA replay. 외부 proxy의 위치·population·clock 제한을 명시하고 Seoul 예측 정확도 또는 자연 장애 회피 개선을 결론내리지 않는다.
R3-F120 보조 비교는 핵심과 같은 B를 사용하여 실제 measured-cost coordinator 대비 고정 운영점의 차이를 본다. dynamic hazard 적응 성능까지 주장하려면 별도 동일 trace pair가 필요하며 현재 필수에서 제외한다.
E2의 FIS 장애는 이 lambda에서 확률적으로 샘플링된 사건이 아니라 사전 고정한 single controlled interruption이다. 실제 IMDS/FIS/EC2 로그는 E2 실행 때 별도 수집한다. FIS1회를 이용해 .05/h를 확인했다고 쓰지 않는다.

5. 최종 실험 실행서

5.1 공통 환경·데이터와 동결 gate

MGMT/Karmada/On-Prem 등록은 유지. 학습 자체는 aws1의 같은 서울 AZ 두 Worker 사이 DDP. NFS private endpoint 10.50.1.98:/mnt/nfs, WireGuard/기존 routing 및 NFS provisioner/default StorageClass를 사용한다. WAN을 가로지르는 학습 throughput 비교가 아니다. NFS 기존 결과·checkpoints·PV/PVC는 보존한다.

5.3 E2 실행 순서(모델별 B/C)

1) 검토된 B의 비교 hash·하드웨어·full-goal·audit·정확한 무장애 상태·비용 적격성을 확인. 부적격이면 B를 새로 실행해야 하며 총6이라는 계산은 늘어날 수 있다.

6) 자연 controller 경로로 긴급 CP·그룹 quiesce·대체 VM·NFS/PVC/fencing·restore를 진행. timing이 맞지 않으면 사전 full-group snapshot을 실제 선택한 근거를 기록. 복원 완료를 수동 patch하지 않는다.
7) source/target provider ID, Node/Pod UID 변화를 확인. saved/restored step, rank audit 및 두 rank actual update/high-water mark 회복, Verified를 모두 관측한다. 실제 목표까지 완료해야 정식 Run이며 Verify 직후 중단한 acceptance와 구분한다.

8. 교수님·IEEE 심사 예상 문제와 대응

- Desai와 신규성이 다른가: 새 위험 식/async engine이 아니라 multi-cluster VM lifecycle, UID/fencing/CP 조율/복원/반환의 관리 계약과 운영 증거다. 차별성이 단순 통합에 머문다면 그 한계도 설명한다.
- E1은 두 요인 동시 변경인가: 운영 패키지 비교로 명시하고 CP 단독 효과로 귀속하지 않는다. R3 인과 주장은 별도 pair로 다룬다.
- .05의 실제 근거는: 실측값이 아니다. low-risk controlled point, bootstrap300초, fixed composition override라는 작용을 제시한다. 예측 정확도 주장은 하지 않는다.
- 왜 US/V100 trace인가: 기존 모델에 연결 가능한 외부 입력이다. Seoul/G5/G6 hazard라 부르지 않는다. population1 가정·causal cutoff·clock을 공개한다.
- Iteration Time을 쓰지 않는가: readiness와 직접 최적화 입력을 분리한다. bootstrap/CRIU cost는 iteration 직접 이용이 없고 async 경로는 미검증이다. 실제 경로에 맞춰 서술한다.
- 복원은 step 출력뿐인가: provider/Pod UID 변화, 동일 round/durable hash, fencing, model/optimizer/RNG/step audit, 실제 update, Verified 및 최종 goal 모두 필요하다.
- FIS1회면 충분한가: 단일 위치의 통제 장애다. 자연 빈도/모든 위치/대규모 일반화는 불가. 반복과 실패를 공개하고 유의성을 만들어내지 않는다.
- Spot이 싸다는 계산 아닌가: GPU lifecycle 전체 및 stall/idle/overlap의 실제 시간 적분을 측정한다. 음수 절감과 실패 비용도 공개한다.
- VM age/network/cache/NFS의 교란은: launch/Ready/image pull/cache/system version/가능한 network·NFS 상태를 기록하고 인접·사전 순서화한다. 미측정 요인을 원인으로 단정하지 않는다.
- 소형 모델로 대규모 일반화 가능한가: 작은 시스템 사례 범위다. ImageNet 정확도/최종 수렴/대규모 elastic LLM/cross-cloud collective는 미검증이다.
- R1의 자동 반환은 검증됐는가: 정상 삭제 요청→실제 종료는 확인했지만 학습 완료 이벤트만으로 Controller가 반환하는 경로는 현재 코드에서 확인되지 않았다. 평가 runner 정리를 완전자동 lifecycle 기여로 바꾸어 쓰지 않는다.
- R5 정량은: AWS-only E1/E2로 증명하지 않는다. I1 구현 증거로 제한하거나 별도 연구로 통제 비교한다.
