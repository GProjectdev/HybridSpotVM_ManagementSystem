# IEEE Access 최종 평가 구성 변경 및 추가 실험 준비

현재 진행 중인 Hybrid Cloud Spot DDP 정량 평가 준비 작업의 최종 실험 구성이 변경되었다.

**기존 v2 계획에서 S1은 4-Rank, S2는 2-Rank로 구분했으나, 최종 평가에서는 E1·E2 모두 4-Rank DDP로 통일한다.**

이번 변경사항을 기존 실험 준비 상태에 반영하라.

실험의 연구 질문과 비교군은 아래 내용으로 확정하며, 임의로 변경하지 마라.

## 1. 최종 평가 구성

### E1. 통합 관리 시스템의 정상 운영 효과

**평가 목적**

기존 All On-Demand 운영과 비교하여, Spot 위험률 기반 자원 관리 및 Checkpoint 조율을 통합한 시스템의 End-to-End 비용·성능 효과를 검증한다.

**비교군**

A. All On-Demand

- 4 On-Demand GPU VM
- 4-Rank DDP
- 주기적 Checkpoint 비활성
- 인위적인 Spot 중단 없음

B. 제안 통합 관리 시스템

- 4개의 GPU Worker 요청
- 기존 위험률·가격 기반 정책으로 Spot/On-Demand 구성 결정
- 실제 구현된 Checkpoint 조율 정책 활성화
- 위험률 변화에 따른 자원 구성 조정 허용
- 인위적인 Spot 중단 없음

**측정 지표**

- 자원 요청부터 목표 학습 완료까지의 시간
- GPU VM Compute Cost
- 유효 학습 처리율
- Checkpoint 횟수 및 실제 Stall Time
- Worker 생성·교체·복원·반환 오버헤드
- 실제 자원 구성 및 Checkpoint 정책 결정 결과

E1은 시스템 전체 운영 방식의 비교이므로 Spot 가격, 자원 관리, Checkpoint의 독립 효과를 분리했다고 주장하지 않는다.

### E2. Spot 선점·복구를 포함한 통합 관리 시스템의 비용–성능 평가

**평가 목적**

실제 Spot Worker 중단과 복구에 따른 추가 운영 부담을 포함하더라도, 제안 시스템이 All On-Demand 운영 대비 어떠한 비용·성능 관계를 보이는지 검증한다.

**비교군**

A. All On-Demand 정상 실행

- E1의 A 결과 재사용 가능

B. 제안 시스템 정상 실행

- E1의 B 결과 재사용 가능

C. 제안 시스템 Spot 선점·복구 실행

- B와 동일한 위험률 입력, 초기 GPU 구성, Checkpoint 정책, 모델·데이터·학습 목표
- 실제 Spot Worker 1대에 AWS FIS 중단 1회 적용
- 대체 Worker 생성 및 기존 Checkpoint/Restore 경로로 학습 복원
- 목표 Step까지 학습 완료

**핵심 비교**

- A vs B: 정상 운영에서 제안 시스템의 비용–성능
- B vs C: 선점 및 복구로 인한 추가 시간·비용
- A vs C: 복구 부담을 포함한 제안 시스템의 비용–성능

A와 C의 비교를 위험률 기반 알고리즘의 독립적 우수성으로 해석하지 않는다.

## 2. 기존 검증 결과 재사용

다음 항목은 기존 증거를 우선 재사용한다.

- GPT-2 Small의 기존 2-Rank DDP 학습 및 복구 검증
- ResNet-50의 동일 Pod C/R 검증
- 기존 GPU 및 Durable Checkpoint 수용검사
- SkyPilot/SARIMA 위험률 입력 및 Collector 연계
- 기존 자원 관리·Checkpoint 정책 코드 분석
- 기존 학습 데이터 및 모델 무결성 확인
- 기존 평가 도구 테스트

기존 검증 결과의 코드·설정·GPU 유형·복구 경로가 이번 정식 실험과 동일한 경우에는 다시 실행하지 마라.

4-Rank에서 새롭게 확인해야 하는 기능만 추가 검증하라.

## 3. 4-Rank DDP 실행 준비

AWS ap-northeast-2c에서 다음 조건을 준비한다.

- GPU VM 4대
- VM당 GPU 1개
- 각 VM에 DDP Rank 1개 배치
- 동일 GPU Instance Type
- Karmada 기반 기존 Member Cluster 활용
- 기존 Checkpoint/Restore 구조 유지

다음을 확인하라.

1. 4-Rank 학습 배포 가능 여부
2. 전체 Rank의 Checkpoint 생성 및 정합성
3. Spot Worker 1개 중단 후 기존 Full-group Restore 지원 여부
4. 복원 이후 전체 Rank의 실제 Optimizer Update 진행
5. 목표 학습 완료 및 VM 정상 반환
6. 대체 Worker 생성 시 Quota·용량·비용 문제

Spot Quota 32의 실제 단위 및 적용 인스턴스 계열을 확인하고, On-Demand Quota도 별도로 확인하라.

기존 Controller와 복구 기술을 대규모 재설계하지 않는다.

## 4. 위험률 입력 및 B·C 비교 조건 확정

현재 확보한 SkyPilot 기반 SARIMA 예측 데이터를 사용한다. 없으면 따로 확보해라.

새로운 위험률 예측 알고리즘이나 장기간 AWS 이력 수집은 진행하지 않는다.

다음을 수행하라.

1. 기존 위험률 입력 및 정책 결정 코드를 확인한다.
2. 실제 Spot/On-Demand 구성에 영향을 주는 위험률 입력을 확인한다.
3. B와 C가 동일한 위험률 시계열과 재생 기준을 사용할 수 있도록 준비한다.
4. 해당 시계열에서 초기 Spot 자원이 생성되는지 확인한다.
5. 사전에 정한 장애 시점에 Spot Worker가 존재하는지 확인한다.
6. 위험률 변화에 따른 자원 전환과 Checkpoint 조율을 기록한다.

**중요**

B와 C는 E2의 정상/선점 대응 비교이므로 동일한 초기 상태와 위험률·Checkpoint 설정을 사용해야 한다.

C에서 중단 시점 전에 모든 Spot VM이 On-Demand로 전환된다면, 해당 조건은 단일 Spot Worker 선점·복구 실험으로 실행할 수 없다.

이 경우 임의로 위험률을 변경하거나 다른 VM을 중단시키지 말고, 설계 충돌을 보고하라.

E1에서 동적 자원 재구성이 관측되어야 한다는 요구와 E2에서 Spot 노출이 유지되어야 한다는 요구가 하나의 입력 시계열에서 양립 가능한지 먼저 확인한다.

양립하지 않으면 서로 다른 위험 입력을 사용하는 실험 블록과 각각의 정상 기준선이 필요한지 보고하되, 연구자 승인 없이 변경하지 마라.

## 5. Checkpoint 정책 및 FIS 준비

B·C의 Checkpoint 정책과 실제 실행 경로가 동일한지 확인한다.

다음 정보를 기록한다.

- 위험률 입력 및 출처
- Checkpoint 정책 분기
- 결정된 주기
- 실제 Checkpoint 시작·완료 시각
- Checkpoint Stall
- 실제 복원된 Step
- 복원 후 재학습 소요시간

기존 보고서에서 미검증된 Iteration Time 기반 비동기 Desai 정책이 실행됐다고 주장하지 않는다.

FIS는 정확히 소유가 확인된 Spot Worker 1대만 대상으로 한다.

이전 FIS IAM Tag 및 Template 관련 오류 수정 사항을 재사용하고, 실제 AWS 실행에서 미확인인 항목만 검증한다.

실제 VM 생성 및 FIS 실행은 사전에 승인된 범위에서만 수행한다.

## 6. 비용 및 성능 계측

A·B·C에 대해 동일한 기준으로 데이터를 수집한다.

- NodeRequest 생성 시각
- GPU VM 생성 및 Ready 시각
- DDP 첫 Optimizer Update
- 목표 학습 Step 완료 시각
- GPU VM 실제 종료 시각
- VM별 Spot/OD 가격과 과금 대상 사용시간
- Checkpoint 및 Restore 이벤트
- DDP Rank별 학습 진전
- Spot interruption 및 FIS 이벤트
- Worker 교체·복원 지연
- 복원 후 이전 학습 진전 수준을 회복하는 데 걸린 시간

모든 GPU 비용에는 최초·대체·중첩·유휴 VM을 포함한다.

EBS/NFS/VPN/FIS 등 제외한 비용은 별도로 명시하고, GPU Compute Cost를 전체 클라우드 비용으로 표현하지 않는다.

정상 실행과 선점 실행은 목표 학습량·GPU 사양·모델·Batch Size·Seed·Checkpoint 정책·위험률 입력이 일치하는 경우에만 대응 비교한다.

## 7. 실험 모델과 반복 계획

기존 모델 및 데이터셋을 우선 사용한다.

- GPT-2 Small / WikiText-103
- ResNet-50 / CIFAR-10

4-Rank에 맞는 Per-Rank Batch Size와 Global Batch Size를 정식 실행 전에 확정한다.

모든 비교군에서 동일 모델에 대한 총 학습량과 목표 Optimizer Step을 유지한다.

GPU 유형이 G5에서 G6로 변경되면 학습 목표 Step 및 실행 설정을 다시 검토한다.

모델별 A·B·C의 기본 비교를 확보한 뒤 주요 조건의 대응 반복을 우선 진행한다.

실패 및 중단된 실행도 기록하고, 성공한 Run만 선택하여 결과를 계산하지 않는다.
